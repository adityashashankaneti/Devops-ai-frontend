## 3-Repo Architecture (Modular Terragrunt + YAML GitOps Pipeline)

All repos live at `C:\Users\Aditya Shashank\Documents\Devops-repos\`:

```
Devops-ai-frontend/    ← REPO 1: React canvas UI (this repo)
  GitHub: adityashashankaneti/Devops-ai-frontend (assumed)

Devops-backend/        ← REPO 2: AWS Lambda (Python) — Claude classifies resources into YAML, pushes to infra-live
  GitHub: adityashashankaneti/Devops-backend

devops-infra-live/     ← REPO 3: Reusable Terraform modules + Terragrunt configs + YAML resource definitions + GitHub Actions CI/CD
  GitHub: adityashashankaneti/devops-infra-live
```

### Architecture Philosophy
- **Claude does NOT generate raw Terraform code.** Claude classifies canvas resources into per-module-type YAML configs.
- **Reusable Terraform modules** under `modules/` accept `for_each = var.resources` (a map of resource configs).
- **Static Terragrunt files** under `environments/dev/<type>/terragrunt.hcl` point at the matching module and read `resources.yaml`.
- **Lambda only appends** new resources to existing `resources.yaml` files (merge/append, not overwrite).
- **GitHub Actions** detects changed project dirs and runs `terragrunt run-all plan/apply` per project.

### End-to-End Deploy Flow
1. User designs infra on canvas (VPC → Subnet → EC2, etc.), sets CIDRs/configs in PropertiesPanel
2. Clicks **Deploy** in DeployBar → frontend POSTs nested JSON to Lambda via API Gateway
3. Lambda calls Claude API with the JSON → Claude **classifies** resources by module type and returns per-type YAML configs (NOT raw .tf code)
4. Lambda merges/appends the YAML configs into `environments/dev/<type>/resources.yaml` files in the `devops-infra-live` repo on branch `feature/<project>` + creates a Pull Request
5. Frontend starts polling `GET /api/status?pr_url=...` every 10s for CI check status
6. GitHub Actions runs `terragrunt run-all plan` on PR → posts plan output as PR comment
7. User reviews and merges PR to main
8. GitHub Actions runs `terragrunt run-all apply -auto-approve` → AWS infrastructure is deployed

## Known Issues / Fixes Applied This Session

1. **`requirements.txt` must be in `src/`** — SAM reads from `CodeUri: src/`, not project root.
   Root `requirements.txt` still exists but SAM uses `src/requirements.txt`.

2. **CORS was missing** — API Gateway was implicit `ServerlessHttpApi`. Fixed by adding explicit
   `DevOpsHttpApi` resource with `CorsConfiguration`. URL changed as a result — update `.env.local`.

3. **AWS CLI JSON quoting on Windows** — PowerShell and bash both mangle JSON quotes when passing
   `--secret-string` inline. Always write to a file and use `file://C:/path/to/file.json`.

4. **`sam validate` needs `--region`** — The validate job runs before AWS credentials are configured,
   so it must receive `--region ${{ env.AWS_REGION }}` explicitly.

5. **Lambda caches Secrets Manager values** — After updating a secret, force a cold start by running:
   `aws lambda update-function-configuration --function-name <name> --description "bump"`

6. **Terragrunt Apply skipped on PRs (by design)** — `terraform.yml` apply job has condition:
   `if: github.event_name == 'push' && github.ref == 'refs/heads/main'`
   Apply only runs when PR is merged to main. Plan runs on PRs. This is intentional.

7. **All `resources.yaml` placeholders were comment-only** — `terragrunt run-all apply` processes
   ALL subdirs under `environments/dev/`, not just changed modules. Any module with a comment-only
   `resources.yaml` caused `yamldecode` to fail ("missing start of document"). Fixed: all 19 placeholder
   `resources.yaml` files now contain `{}` (valid empty YAML). This includes: alb, cloudfront, dynamodb,
   ec2, ecs, elasticache, eventbridge, internet-gateway, lambda, nat-gateway, rds, route-table, route53,
   s3, security-group, sns, sqs, subnet, vpc.

8. **Frontend showed `✗` for skipped CI jobs** — `DeployBar.tsx` only checked `conclusion === 'success'`
   vs everything-else. GitHub returns `conclusion: 'skipped'` for jobs whose `if:` condition was false.
   Fixed: skipped now shows `⊘ skipped` with muted gray styling in both the in-progress row and the
   success row.

9. **Apply failures were invisible in frontend after PR merge** — `get_pr_status()` in `git_push.py`
   read check runs only from `pr.head.sha`. But apply runs on the merge commit (push to main), which is
   a different SHA. Fixed: when `pr.merged` is true, also fetch check runs from `pr.merge_commit_sha`
   and include them in `all_checks`.

10. **`overall_status` stayed `"pending"` when Apply was skipped on PR** — Old logic:
    `all(c == "success")` — fails because `"skipped" != "success"`. Fixed: skipped/neutral conclusions
    are now treated as non-failures. overall becomes `"success"` when all conclusions are in
    `("success", "skipped", "neutral")` and at least one actionable (non-skipped) conclusion exists.

11. **Root `terragrunt.hcl` couldn't find `project.yaml`** — `environments/terragrunt.hcl` line 49 used
    `file("project.yaml")` which resolves relative to `environments/` (where the root HCL lives).
    But `project.yaml` is written by Lambda to `environments/dev/project.yaml`. Fixed by changing to
    `file(find_in_parent_folders("project.yaml"))` — `find_in_parent_folders` resolves from the child
    module's directory context (e.g. `environments/dev/alb/`) and correctly traverses up to find
    `environments/dev/project.yaml`.

12. **S3 remote state bucket name collision** — `bucket = "${local.project}-tf-state"` resolved to
    `my-infra-tf-state` which is a globally unique S3 name already taken by another AWS account.
    Fixed: `bucket = "${local.project}-tf-state-${get_aws_account_id()}"` and same for DynamoDB lock table.
    Terragrunt `get_aws_account_id()` is a built-in that returns the current AWS account ID.

## New Features Added (Session 2)

### 1. Import State (GET /api/import)
Reads all `terraform.tfstate` files from `s3://{project}-tf-state-{account_id}/environments/dev/*/`
and returns ReactFlow-compatible nodes and edges for the canvas.

- **Backend:** `src/import_state.py` — S3 state parser. Maps Terraform resource types (aws_vpc, aws_subnet, etc.)
  to frontend resource IDs. Builds layout: VPCs as large containers, subnets nested inside, others in a grid below.
- **Frontend:** "Import State" button in DeployBar. Uses `VITE_IMPORT_URL`. On success, dispatches
  `load-canvas` custom event to replace canvas nodes/edges. Also calls `onImportSucceeded` callback
  which marks all imported nodes as deployed (green + locked).
- **IMPORTANT:** Always select `us-west-2` region (matches project.yaml) when importing.

### 2. Deployed Node State (Green + Locked)
After deploy apply succeeds OR after Import State, nodes are marked as deployed in localStorage
under key `devops-deployed-nodes: Record<nodeId, DeployedNodeInfo>`.

**DeployedNodeInfo shape:**
```typescript
{ project: string; region: string; resourceType: string; resourceName: string }
```

**Visual:** Deployed nodes get green border + `🔒 live` badge.
- `AWSNode`: green border ring + "live" label
- `ContainerNode`: solid green border (replaces dashed), green-tinted bg

**Locking:** `handleNodesChange` in ArchitectureCanvas filters out `remove` changes for deployed node IDs.
Shows toast: "Deployed resources are locked. Use Destroy in the Properties panel..."

**State management (`App.tsx`):**
- `deployedNodes: Record<string, DeployedNodeInfo>` — loaded from/saved to localStorage
- `pendingBatch` — captured when Deploy is clicked (node IDs + resource info)
- `handleDeployStarted(project, region)` — captures pending batch from current canvas nodes
- `handleApplySucceeded()` — promotes pending batch to deployed (called when `pr_merged && overall_status === 'success'`)
- `handleImportSucceeded(nodes, project, region)` — marks imported nodes as deployed
- `handleNodeDestroyed(nodeId)` — removes from deployed state + dispatches `delete-canvas-node` event

**Context:** `src/contexts/DeployedNodesContext.ts` — React context providing `ReadonlySet<string>` of
deployed node IDs. `AWSNode` and `ContainerNode` use `useIsNodeDeployed(id)` hook to style themselves.
App.tsx wraps everything in `<DeployedNodesContext.Provider value={deployedNodeIds}>`.

### 3. Destroy Resource (POST /api/destroy)
Removes a specific resource from `resources.yaml` and commits directly to main (no PR).
Direct push to main triggers the apply workflow which runs `terraform destroy` for that resource.

**Backend:**
- `git_push.py`: `push_destroy_to_main(github_token, repo_name, project, resource_type, resource_name, commit_message)`
  — reads YAML, deletes the key, commits to main, returns `{ commit_sha }`
- `git_push.py`: `get_commit_status(github_token, repo_name, commit_sha)`
  — polls check runs on a specific commit SHA (same logic as PR status but for direct commits)
- `handler.py`: `POST /api/destroy` — body: `{ project, region, resource_type, resource_name }`
- `handler.py`: `GET /api/commit-status?sha=<sha>` — returns `{ overall_status, checks, commit_sha }`

**Frontend (PropertiesPanel):**
Deployed nodes show a "Destroy Resource" button in the Properties panel footer.
Destroy flow phases: `idle → confirm → destroying → polling → success/error`
- `confirm` phase: shows inline confirm box with resource name + warning text
- `destroying` phase: POSTs to `VITE_DESTROY_URL`
- `polling` phase: polls `VITE_COMMIT_STATUS_URL?sha=...` every 8s
- `success` phase: calls `onNodeDestroyed(nodeId)` → App.tsx removes from canvas + deployed state
- `error` phase: shows error with "Try again" link

**Canvas removal on destroy success:**
ArchitectureCanvas listens for `delete-canvas-node` custom event (dispatched by App.tsx).
Also removes all edges where source or target === destroyed nodeId.

### 6. Import URL region issue
The import reads from `s3://{project}-tf-state-{account_id}/`. The actual deployed project is
`my-infra` in `us-west-2`. Always select `us-west-2` in the deploy bar region dropdown before
clicking Import State. Wrong region in the request doesn't fail S3 access (S3 is global) but
may confuse bucket resolution in future if region-specific paths are added.

### 7. .env.local changes need dev server restart
Vite does NOT hot-reload `.env.local`. After adding new `VITE_*` vars, must `Ctrl+C` → `npm run dev`.
